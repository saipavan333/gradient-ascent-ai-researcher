Compression: prediction and compression are the same thing

Entropy isn’t just a number — it’s a hard limit on how small data can be squeezed. Building an optimal code from scratch reveals a profound idea: a model that predicts well is exactly a model that compresses well. That equivalence is the deep reason learning works.

We close the information-theory track where Shannon started: compression. His source coding theorem says entropy is the floor — you cannot losslessly compress below it, and clever codes reach it. Building one (Huffman coding) from scratch makes entropy tangible. And it exposes a beautiful truth that reframes all of machine learning: compression and prediction are two views of the same thing.

💡 Concept: give frequent symbols short codes

To store a sequence of symbols in as few bits as possible, assign short codes to frequent symbols and long codes to rare ones — Morse code’s exact idea. The optimal length for a symbol of probability \(p\) is its surprise, \(-\log_2 p\) bits (Lesson 0). Averaging over the distribution, the best achievable bits-per-symbol is the entropy \(H\). Huffman coding builds a provably optimal prefix code (no code is a prefix of another, so it decodes unambiguously) by repeatedly merging the two least-frequent symbols into a subtree:

\[ H \;\le\; \text{average code length} \;<\; H + 1 \quad\text{bits per symbol (Shannon).} \] (4.1)

📐 A model is a compressor

Here is the payoff. To compress data, you need a probability for each symbol — and the number of bits you spend is \(-\log_2 p(\text{symbol})\). That is exactly the cross-entropy loss (Lesson 1). So a model that assigns higher probability to the data it sees is a model that encodes that data in fewer bits. The better your predictions, the better your compression, quantitatively and identically:

\[ \text{total bits to encode the data} = \sum_i -\log_2 q(x_i) = (\text{cross-entropy loss}) \times (\text{length}). \] (4.2)

This is why a language model’s quality is measured in bits-per-character (or perplexity): a GPT that reaches, say, 1 bit/character on English has, in the same breath, learned to compress English 8× — and modern LLMs are, formally, among the best text compressors ever built. Training a predictor and building a compressor are the same optimization. The idea runs deeper still: many researchers argue that compression is understanding — to predict (and thus compress) data well, a model must capture its underlying structure.

The whole track, in one sentence. Entropy is the cost of the data; cross-entropy is the cost your model pays; KL is the excess you pay for being wrong; mutual information is the cost you save by using a related variable; and compression is what all of it buys you. Every loss you’ve minimized in this curriculum was, underneath, a number of bits — and learning was the act of finding the shortest description of the data.

✍️ Worked example: coding four symbols

Give frequent symbols short codes. Take \(A:\tfrac12,\ B:\tfrac14,\ C:\tfrac18,\ D:\tfrac18\).

1
Optimal lengths. \(-\log_2 p\): A→1 bit, B→2, C→3, D→3. Assign codes A=0, B=10, C=110, D=111 (a prefix code — no code is a prefix of another).
2
Average length. \(\tfrac12(1)+\tfrac14(2)+\tfrac18(3)+\tfrac18(3)=1.75\) bits/symbol.
3
The entropy. \(H=-\sum p\log_2 p = 1.75\) bits — the optimal code exactly hits the entropy. That's no coincidence: Shannon's theorem says the best possible average code length is the entropy.
4
Versus fixed-length. A naive 2-bits-per-symbol code wastes \(2-1.75=0.25\) bits per symbol — a 12.5% saving from matching code length to frequency, and it grows as the data gets more skewed.

🔑 Key results to remember

  • Source coding theorem: you can’t losslessly compress below the entropy \(H\); good codes get within 1 bit.
  • Huffman coding builds an optimal prefix code by merging the two least-frequent symbols repeatedly.
  • Optimal code length for a symbol of probability \(p\) is its surprise \(-\log_2 p\).
  • Compression = prediction: bits to encode data \(= \sum -\log_2 q(x_i) =\) cross-entropy × length.
  • A better predictor is a better compressor — LLM quality (bits/char, perplexity) is literally a compression rate.

⚠️ Mistakes everyone makes here

  • Thinking you can beat entropy. No lossless code can average fewer than \(H\) bits/symbol. Entropy is a hard floor, not a target you can undercut.
  • Ignoring the model. Compression is only as good as your probability model. A better model (lower cross-entropy on the data) compresses better — which is why "a language model is a compressor."
  • Forgetting the prefix property. Variable-length codes must be uniquely decodable; prefix-free codes (like Huffman) guarantee it. Random short codes can be ambiguous.
  • Confusing lossless with lossy. Entropy bounds lossless coding. Lossy schemes (JPEG, MP3) throw away information you won't miss to go further — a different game.

Q1. Shannon’s source coding theorem says the average bits per symbol for lossless compression…

  • can be made arbitrarily small.
    No — there’s a hard floor. You can’t compress below the entropy without losing information.
  • equals the number of distinct symbols.
    That would be a fixed-width code; entropy-based coding does far better when symbols are unequal.
  • cannot go below the entropy \(H\), and optimal codes get within 1 bit of it.
    Correct. Entropy is the theoretical minimum bits/symbol; Huffman achieves between \(H\) and \(H+1\), reaching the floor as you code longer blocks.
  • is always 8 (one byte).
    8 bits is fixed-width ASCII, which is wasteful; entropy coding beats it for structured data.

Q2. Huffman coding assigns…

  • shorter codes to more frequent symbols.
    Correct. By merging the two least-frequent symbols repeatedly, frequent symbols end up nearer the tree’s root and get shorter codes — minimizing the expected length.
  • the same length to every symbol.
    That’s fixed-width coding; Huffman’s advantage is variable-length codes matched to frequency.
  • longer codes to more frequent symbols.
    Backwards — that would make the encoding longer, the opposite of the goal.
  • codes at random.
    Huffman is a deterministic, optimal construction based on frequencies.

Q3. Why are compression and prediction “the same thing”?

  • They both use trees.
    Superficial at best; the equivalence is about bits and probabilities, not data structures.
  • They’re actually unrelated.
    They’re formally identical — that’s the lesson’s core point.
  • Compression needs no model.
    Optimal compression needs a probability model of the data — exactly a predictor.
  • Encoding a symbol costs \(-\log_2 q(\text{symbol})\) bits, which is exactly the cross-entropy loss — so higher predicted probability means fewer bits.
    Correct. The bits to store the data under model \(q\) equal its cross-entropy times the length; minimizing prediction loss is minimizing code length. A better predictor is, identically, a better compressor.

Q4. A language model reaches 1 bit/character on English (vs 8-bit ASCII). This means it…

  • runs 8× faster.
    Bits/character is about predictive quality/compression, not speed.
  • can compress English text about 8×, because it predicts the next character well enough to encode it in ~1 bit.
    Correct. 1 bit/char vs 8 bits/char is an 8× compression rate — the model’s sharp next-character distribution means each character costs ~1 bit under Equation (4.2). LLMs are, formally, excellent compressors.
  • has 1 billion parameters.
    Bits/character is a performance measure, unrelated to parameter count.
  • uses a 1-character context.
    Reaching 1 bit/char requires long context to predict well; short context gives higher bits/char.

✍️ Practice

1. Run compression.py. Confirm the Huffman average is between \(H\) and \(H+1\). Then feed it highly repetitive text (e.g. “aaaaab”) — what happens to the compression ratio?

Show solution

The average code length always falls in \([H, H+1)\), as Shannon guarantees. Highly skewed text like “aaaaab” has very low entropy (one symbol dominates), so it compresses dramatically — Huffman gives ‘a’ a 1-bit code and the rare ‘b’ a longer one, and the bits/char drops far below the ~4.4 of natural English. This is entropy in action: the more predictable (lower-entropy) the source, the more it compresses. It also hints at Huffman’s limitation — it codes symbols independently, so it can’t exploit that ‘aaaa’ is even more predictable than single-‘a’ statistics suggest; capturing such context is exactly what a predictive model (and arithmetic coding) does.

2. Huffman uses whole-bit code lengths, so it can waste up to ~1 bit/symbol. How do modern compressors (and LLMs) close that gap?

Show solution

Two ways. First, arithmetic coding (and range coding) encode an entire message as a single number, effectively assigning fractional bits per symbol, so they reach the entropy limit without the up-to-1-bit rounding waste of per-symbol codes. Second — and more powerfully — better probability models: Huffman used single-symbol frequencies, but conditioning each symbol on its context (previous characters) sharply lowers the entropy, so there are fewer bits to spend in the first place. A neural language model provides exactly this context-dependent \(q(\text{next}\mid\text{context})\); paired with arithmetic coding it becomes a state-of-the-art compressor. The frontier of compression is therefore the frontier of prediction — the same models.

3. Conceptual: some researchers propose evaluating (and even defining) intelligence via compression. What’s the argument, and what’s a caveat?

Show solution

The argument (e.g. the Hutter Prize, and the “compression = intelligence” thesis): to compress data optimally you must model its structure, and the deeper the regularities you capture — grammar, facts, reasoning patterns — the shorter your encoding. So the ability to losslessly compress a rich corpus is a measurable proxy for how much structure a system has understood, and improving it forces genuine modelling rather than memorization. The caveat: compression rewards capturing statistical structure, which isn’t identical to understanding, agency, or reasoning in every sense; a superb text compressor need not be able to act in the world or verify truth. Still, the equivalence you proved in this lesson — prediction is compression is cross-entropy — is why next-token prediction, a “mere” compression objective, has proven such a powerful path toward capable models. It’s a fitting place to end the theory: the losses you minimized were bits, and squeezing them out is, in a precise sense, learning.

🚀 In the real world & at the frontier

Compression and prediction are two sides of one coin: to compress data you need a model of it, and a better model gives better compression — the average code length is exactly the cross-entropy of your model on the data. This is why "compression = intelligence" is a serious idea: a model that compresses text extremely well must have learned its structure. Large language models are, quite literally, powerful compressors of their training data (their loss is measured in bits/token), and some researchers use compression benchmarks to measure model quality. Shannon's 1948 coding theorem — that entropy is the ultimate limit — turned out to describe the objective at the heart of modern AI.

Recap — say it to a friend

"Give frequent symbols short codes and rare ones long codes, and the best you can do is an average of \(H\) bits per symbol — the entropy — which Shannon proved is a hard floor. Optimal code length is \(-\log_2 p\). Compression needs a probability model, and a better model compresses better, because average code length equals the cross-entropy of your model. That's why 'a good language model is a good compressor.'"

Designing experiments

A result you can trust is built long before the code runs — in the design. A good experiment changes exactly one thing, holds everything else fixed, writes down what it expects in advance, and runs enough times to tell a real effect from random luck.

Track 22 · Lesson 0 Concept + code + interactive ~24 min Builds on: Tracks 4, 21

You changed the model and the learning rate and the dataset, and accuracy went up. Which change helped? You genuinely cannot tell — and no amount of extra runs will rescue a study that was designed to be ambiguous. The core of experiment design is the one-variable rule: to learn what causes an effect, change a single thing (the independent variable), measure the outcome (the dependent variable), and hold everything else fixed (the controls). Anything that changes alongside your variable and could also explain the result is a confound — the silent villain of bad experiments. Get the design right and the analysis is easy; get it wrong and no statistic can save you.

💡 Intuition: a fair taste test

You want to know whether a new coffee bean makes better coffee. So you brew a cup with the new bean — but you also switch to a different machine, grind finer, and use hotter water. The coffee's better! Was it the bean? You have no idea, because four things changed at once. A fair taste test keeps the machine, grinder, water, and cup identical, and changes only the bean. If the coffee improves, it's the bean — nothing else could be responsible. If you'd also switched the machine, the machine and the bean would be confounded: tangled together so tightly you can't credit either one.

Every ML experiment is a taste test. The bean is your independent variable (a new component, an optimizer, a data change). The cup of coffee is your metric (accuracy, loss). The machine, grinder, and water are the controls — architecture, epochs, data splits, seeds — that you must hold identical on both sides. The entire art is refusing to change more than one thing at a time, no matter how tempting it is to "improve everything at once."

Concretely, a well-designed experiment nails down four things before running:

  • The hypothesis — a specific prediction, e.g. "adding dropout raises test accuracy," written down in advance.
  • The one variable — the single knob you'll change (dropout on vs off).
  • The controls — everything held fixed on both sides (same architecture, epochs, data, seeds, compute).
  • The success criterion — how big an effect counts, decided before you look, e.g. "the gap must exceed twice the run-to-run noise."

The interactive makes the danger visual: in Confound mode you'd proudly report the full height as "the method's effect," but part of it belongs to the extra compute you also handed it. This is why fair comparison means same tuning budget, same compute, same data, same evaluation on both sides. A method that only wins because it was given more of everything hasn't been shown to win at all.

One more pillar: repeats and noise. Because a random seed makes each run wobble, a single run can mislead. Run several seeds and report a mean with its spread (standard deviation). And ask about power — the ability of your experiment to detect an effect of a given size. A tiny true effect drowned in large run-to-run noise needs many runs to see; if you only run twice, you may miss a real effect (or "find" a fake one). Deciding how many seeds to run is part of the design, not an afterthought.

✍️ Worked example: does dropout actually help?

Hypothesis: "adding dropout (randomly zeroing some activations during training, to curb overfitting) raises test accuracy." Let's design the study two ways — the tempting-but-broken way, then the clean way.

1
The broken design. You add dropout and train 50 more epochs and widen the network — accuracy goes 90.0 → 92.0. You excitedly credit dropout. But three things changed; the +2.0 could be the extra epochs or the extra width. The result is uninterpretable no matter how clean the number looks.
2
The clean design. Fix the architecture width, the epoch count, the data splits, and the seed set. Change only dropout (off vs 0.5). Decide the success criterion up front: the gap must exceed twice the combined run-to-run noise.
3
Run several seeds each. No dropout (5 seeds): 90.1 ± 0.3. With dropout (5 seeds): 90.9 ± 0.2. The difference is +0.8.
4
Check against your pre-set bar. Combined noise ≈ √(0.3² + 0.2²) ≈ 0.36, so "twice the noise" ≈ 0.72. The +0.8 gap clears it. Verdict: credible evidence that dropout helps here, on this model and data. Because you changed only dropout, you can actually say "dropout caused the gain" — the sentence the broken design could never earn. Design first; the statistics were the easy part.

🛠️ A controlled experiment loop

Good design shows up in code as a fixed config that you touch in exactly one place, wrapped in a loop over seeds. Everything in BASE is a control; only the loop variable changes.

import numpy as np

BASE = dict(width=256, epochs=100, lr=0.1, augment=True)   # controls: held fixed

def run(dropout, seed):
    cfg = {**BASE, "dropout": dropout, "seed": seed}        # change exactly ONE thing
    return train_and_eval(cfg)

for dropout in (0.0, 0.5):                                  # the single variable
    scores = [run(dropout, s) for s in range(5)]           # repeat over seeds
    print(f"dropout={dropout}:  {np.mean(scores):.2f} ± {np.std(scores):.2f}")

# dropout=0.0:  90.10 ± 0.30
# dropout=0.5:  90.90 ± 0.20   -> +0.80 gap > ~0.72 noise band: credible

⚠️ Mistakes everyone makes here

  • Changing several things at once. The cardinal sin. If the method, the schedule, and the data all changed, the result is uninterpretable — full stop.
  • An unfair baseline. Comparing your carefully tuned method to an untuned or under-resourced baseline confounds "better method" with "more effort."
  • One seed. A single run can't distinguish a real effect from a lucky draw. Repeat and report mean ± std.
  • Moving the goalposts. Deciding what counts as success after seeing the numbers lets you rationalize any result. Set the criterion first.
  • Ignoring compute as a confound. Extra parameters, epochs, or data are the sneakiest confounds — a "better" method that simply got more compute hasn't been shown to be better.
  • Too few runs to see the effect. If the true effect is small and the noise is large, an underpowered study will miss it. Plan the number of seeds around the effect size you care about.

🔑 Key ideas to remember

  • Change one variable, hold the rest fixed. That's what makes a result interpretable.
  • Independent variable = what you change; dependent variable = what you measure; controls = what you freeze; confound = anything that sneaks along with your variable.
  • Fair comparison: same data, tuning budget, compute, and evaluation on both sides.
  • Repeat over seeds; report mean ± std. A single run is a single dice roll.
  • Decide the hypothesis and success criterion before you look, and run enough seeds to have the power to see the effect.

🧩 Check your understanding
Answer from memory, then read why.

Q1. You add a new attention module, and at the same time double the training epochs. Accuracy rises. What's the problem?

  • Nothing — accuracy went up.
    The number rose, but you can't say why, which was the whole point.
  • You should have used a smaller learning rate.
    Unrelated; the flaw is that two variables changed together.
  • Epochs and the module are confounded — you can't attribute the gain.
    Correct. Two variables changed at once, so the improvement could be from either; a clean design changes only the module.
  • Accuracy is the wrong metric.
    The metric isn't the issue; the confounded design is.

Q2. Why report a mean ± standard deviation over several seeds instead of a single run?

  • A single run is one dice roll and can't separate a real effect from luck.
    Correct. Repeats reveal the run-to-run spread, so you can judge whether a gap exceeds the noise.
  • Because more runs always increase accuracy.
    Repeating doesn't raise accuracy; it characterizes variability.
  • To make the experiment take longer.
    Time cost is a side effect, not the reason.
  • Because reviewers like big tables.
    The reason is statistical, not cosmetic.

Q3. A "confound" in an experiment is best described as:

  • The metric you report.
    That's the dependent variable.
  • The thing you deliberately change.
    That's the independent variable.
  • A random seed.
    A seed causes noise, but a confound is specifically a variable tangled with your independent variable.
  • A variable that changes alongside your independent variable and could also explain the result.
    Correct. Confounds are the reason "change one thing" matters — they let a second cause masquerade as your effect.

Q4. Why set the success criterion (e.g., "gap > twice the noise") before running?

  • Because it makes the model train faster.
    It has nothing to do with training speed.
  • So you can't rationalize whatever number you happen to get afterward.
    Correct. Deciding the bar in advance prevents "moving the goalposts" — a form of self-deception where any result gets spun as a success.
  • Because the criterion changes the data.
    It doesn't touch the data; it's a commitment about interpretation.
  • It isn't important; decide after seeing results.
    Deciding after seeing results is exactly the bias this guards against.

✍️ Practice

1. (warm-up) In the interactive, set the true effect to 1.0 and compare Isolate vs Confound mode. In Confound mode, how many points would you wrongly credit to the method, and why is that dishonest?

Show solution

In Isolate mode the bar rises by exactly 1.0 — the true effect. In Confound mode it rises by 1.0 + the hidden compute bonus (about 2.2), so you'd credit roughly 3.2 points to the method when only 1.0 belongs to it. It's dishonest because the extra compute, not the idea, produced most of the gain — you'd be reporting an inflated effect that wouldn't hold if the baseline were given the same resources.

2. (transfer) You want to test whether a new optimizer beats Adam. Write down the independent variable, the dependent variable, three controls you'd hold fixed, and your success criterion.

Show solution

Independent variable: the optimizer (new vs Adam). Dependent variable: test accuracy (or final validation loss). Controls (fixed on both sides): the model architecture, the dataset and its train/val/test splits, the number of epochs, the batch size, and the same set of random seeds — and, crucially, the same tuning budget for each optimizer's learning rate so neither gets an unfair search advantage. Success criterion: decided in advance, e.g. "the mean accuracy gap across 5 seeds must exceed twice the combined standard deviation." Only then does a win mean the optimizer, not the effort.

3. (stretch) Your true effect is about 0.2 points but each run wobbles by ±0.5. You run 3 seeds and see no clear difference. Does that prove the effect is zero? What determines whether you could have detected it?

Show solution

No — it doesn't prove zero; it means your experiment was underpowered. Whether you can detect an effect depends on its size relative to the noise and on how many runs you average: the uncertainty in a mean shrinks like the noise divided by √(number of runs). With ±0.5 noise per run and only 3 seeds, the uncertainty in each mean is about 0.5/√3 ≈ 0.29 — larger than the 0.2 effect, so it's invisible. To see a 0.2 effect you'd need many more seeds (roughly, enough that 0.5/√n shrinks well below 0.2, i.e. dozens of runs). "No difference found" in an underpowered study is not "no effect" — it's "we couldn't have seen it either way."

🚀 In the real world & at the frontier

The "how many seeds?" question turns out to be quantitative: Bouthillier et al. (2021) measured how much of a benchmark's variance comes from random seeds, data ordering, and initialization, and gave concrete guidance on the number of runs needed for a trustworthy comparison. The idea of power and effect size is old — Jacob Cohen formalized it for the behavioral sciences in 1988 — but ML is only now importing it seriously, because compute finally makes many-seed studies feasible. And borrowing from the broader reproducibility movement (Munafò et al.'s "manifesto for reproducible science"), some ML researchers now pre-register hypotheses and analysis plans before running, so the design can't be quietly bent to fit whatever the data happened to show. Good design is becoming a measurable, teachable discipline — not a matter of taste.

Recap — say it to a friend

"To learn what causes what, change one thing and freeze everything else — like a fair taste test. Give both sides the same compute and data, run several seeds, and decide up front how big a gap counts. Design it right and the statistics are trivial; design it wrong and no math can fix it."

Data & model parallelism: training on many machines

Modern models are trained on thousands of GPUs. Data parallelism splits the batch across workers and averages their gradients; model parallelism splits one giant model across devices. Both let you train what no single machine could.

Track 19 · Lesson 3 Concept + code + interactive ~18 min Builds on: Track 2

The other side of efficiency is scale: some models are so large, and trained on so much data, that no single machine could ever do the job — a frontier language model might train on thousands of GPUs for months. Making that work is parallelism: splitting the training across many devices. There are two fundamental ways to split, and understanding them is understanding how large-scale AI is actually built. The first, data parallelism, handles the case where your data is huge: put a full copy of the model on every worker, split each batch of data among them, let each compute gradients on its slice, then average the gradients and everyone applies the same update. The beautiful fact is that this is mathematically identical to training on the whole batch on one machine — just faster, because the work was shared. The second, model parallelism, handles the case where the model itself is too big to fit on one device: split the model across devices, so each holds part of it and the data flows through them like an assembly line. Real systems combine both. This lesson builds data parallelism from its exact gradient math and explains when you need model parallelism instead.

💡 Intuition: divide the work, combine the results

Data parallelism is like grading a huge stack of exams with a team of teaching assistants who all use the same answer key. Split the stack among the TAs; each grades their pile; then combine the results. Since they all used the same key (the same model), combining their grades gives exactly what one person grading the whole stack would have — just done in a fraction of the time. In training, the "grade" is the gradient, the "answer key" is the current model, and "combining" is averaging the gradients. Model parallelism is different: it's for when the answer key is so enormous it doesn't fit in one person's hands. You split the key itself across several people, and each exam passes through all of them in turn, each applying their portion — an assembly line for one huge model.

The exactness of data parallelism comes from a simple property of gradients: the gradient of a sum is the sum of the gradients. So the full-batch gradient equals the (size-weighted) average of the per-shard gradients:

\[ \nabla \mathcal{L}_{\text{full batch}} \;=\; \frac{1}{N}\sum_{i=1}^{N} \nabla \ell_i \;=\; \sum_{k=1}^{W} \frac{n_k}{N}\,\big(\text{worker } k\text{'s average gradient}\big) \] (3.1)

Read it: the full-batch gradient is the average of the per-example gradients \(\nabla\ell_i\) over all \(N\) examples. Group the examples by worker: each worker \(k\) computes the average gradient over its \(n_k\) examples, and the overall gradient is those worker-gradients averaged (weighted by shard size \(n_k/N\)). No approximation — it's the same number, just computed in parallel. Every worker then applies this identical averaged gradient, so all copies of the model stay in lockstep.

🛠️ From scratch: data parallelism

shards = np.array_split(batch, num_workers)          # split the batch across workers

# single machine (for comparison):
g_single = grad(full_batch)

# data-parallel: each worker's gradient on its shard, size-weighted, then averaged
g_parallel = sum(grad(shard) * len(shard) for shard in shards) / len(batch)

assert np.allclose(g_single, g_parallel)             # EXACTLY equal — no approximation

The whole method is "compute gradients on shards, average them" — the averaging (an all-reduce in real systems) is the only communication needed. Because the result is exact, data parallelism scales to thousands of workers with no change to what's being computed; the practical limit is the communication cost of averaging gradients across all those machines each step.

The zoo of parallelism (how frontier models train). Real large-scale training stacks several kinds. Data parallelism (this lesson) splits the batch. Tensor parallelism splits individual layers (matrix multiplies) across devices. Pipeline parallelism splits the layers into stages, like an assembly line, with batches flowing through. Fully-sharded data parallelism (FSDP/ZeRO) even splits the optimizer state and weights to save memory. A model like GPT is trained with a carefully tuned combination — "3D parallelism" — because no single strategy handles both huge data and huge models. But data parallelism, the exact one you built, is the foundation they all extend.

⚠️ Mistakes everyone makes here

  • Thinking data parallelism changes the result. It doesn't — the averaged gradient is exactly the full-batch gradient. Only speed changes (up to communication cost).
  • Forgetting communication is the bottleneck. Averaging gradients across many workers every step costs bandwidth; at large scale, communication — not computation — often limits speedup.
  • Using data parallelism when the model doesn't fit. Data parallelism needs a full model copy per worker. If one model doesn't fit on one device, you need model/tensor/pipeline parallelism instead.
  • Ignoring the effective batch size. N workers make the effective batch N× bigger, which can need learning-rate tuning (the "large batch" training regime) to train well.

🔑 Key results to remember

  • Data parallelism: copy the model to every worker, split the batch, average the gradients — exactly equals single-machine training (eq 3.1), just faster.
  • Model parallelism: split one too-big model across devices (data flows through them) — for when the model doesn't fit.
  • Averaging gradients (all-reduce) is the only communication data parallelism needs.
  • Communication cost is the practical limit to scaling, not the math.
  • Frontier training combines data + tensor + pipeline (+ sharding) parallelism.

Q3. When do you need model parallelism instead of data parallelism?

  • When the model is too big to fit on one device.
    Correct. Data parallelism needs a full model per worker; model parallelism splits the model itself.
  • When the data is small.

  • When you have only one GPU.

  • The math becomes wrong.

  • The number of layers.
    Layer count isn't the scaling limit.
  • Communication cost of averaging gradients across workers.
    Correct. All-reduce bandwidth becomes the bottleneck at large scale.
  • The learning rate.
    A tuning concern, not the fundamental scaling limit.

✍️ Practice

1. (warm-up) In the interactive, go from 1 to 8 workers. How does step time change, and does the readout say the result changed?

Show solution

Step time falls roughly in proportion to the number of workers (8 workers ≈ 1/8 the time, in the ideal shown), because the batch's work is shared. Crucially, the readout confirms the averaged gradient is exactly the single-machine gradient at every worker count — the result never changes, only the speed. That combination — more speed, identical answer — is the whole appeal of data parallelism, and it's why it's the default first step for scaling training. In reality the speedup is slightly sub-linear because averaging gradients across workers costs communication time, which the idealized widget omits; that communication overhead is what eventually caps the benefit of adding more workers.

2. (transfer) With 1000 workers, communication (averaging gradients every step) can dominate. Name one way to reduce communication cost.

Show solution

Several approaches. (1) Gradient accumulation / larger local batches: each worker does more computation between syncs, so you communicate less often per unit of work (fewer, bigger steps). (2) Gradient compression: quantize or sparsify the gradients before sending them, cutting the bytes per all-reduce (at some accuracy risk). (3) Efficient all-reduce algorithms like ring all-reduce, which spread the communication evenly across workers so bandwidth scales well instead of bottlenecking at one server. (4) Overlap communication with computation: start averaging early layers' gradients while later layers are still computing, hiding the communication behind the backward pass. (5) Better interconnects (NVLink, InfiniBand) — hardware co-design. Real large-scale training uses several of these together; managing the communication-vs-computation balance is a core part of making thousand-GPU training efficient, and it's why simply adding more workers eventually stops helping.

3. (stretch) A trillion-parameter model won't fit on one GPU and trains on enormous data. Sketch how you'd combine parallelism types to train it.

Show solution

You'd stack complementary strategies ("3D parallelism"). First, because the model doesn't fit on one device, split it: use tensor parallelism to divide each big layer's matrix multiplies across a small group of GPUs (e.g., 8 GPUs in a server sharing one layer), and pipeline parallelism to split the model's layers into stages across groups of GPUs, with micro-batches flowing through the pipeline like an assembly line to keep every stage busy. That handles the "model too big" problem — one full model copy now spans many GPUs. Then, to handle the huge data, wrap the whole thing in data parallelism: replicate that multi-GPU model across many such groups, each processing a different shard of the batch, and average gradients across the replicas. Optionally add sharding (ZeRO/FSDP) to split optimizer states and reduce memory further. The result is thousands of GPUs organized in a hierarchy — tensor-parallel within a server, pipeline-parallel across a few servers, data-parallel across the whole cluster — each dimension chosen so communication stays on the fastest available links. This is genuinely how frontier models are trained, and the exact data-parallel gradient averaging you built here is the outermost, foundational layer of that hierarchy.

🚀 In the real world & at the frontier

Parallelism is what makes large-scale AI physically possible: every frontier model is trained on hundreds to tens of thousands of accelerators using a carefully engineered mix of data, tensor, and pipeline parallelism, plus memory-sharding techniques like ZeRO and FSDP. The engineering — keeping thousands of GPUs busy, hiding communication behind computation, recovering from hardware failures mid-run — is as much of the achievement as the model design. The frontier pushes toward ever-larger clusters, faster interconnects, and smarter overlap of communication and compute, as well as decentralized and asynchronous training. This closes the efficiency toolkit from the other direction: distillation, pruning, and quantization make a trained model small enough to deploy; parallelism makes training a huge model possible in the first place. Together they span the full lifecycle of practical large-scale machine learning.

Recap — say it to a friend

"To train on huge data, use data parallelism: put the model on every worker, split the batch, and average the gradients — which is exactly the full-batch gradient (gradient of a sum = sum of gradients), just computed in parallel. To train a model too big for one device, use model parallelism: split the model across devices. Frontier models combine both, and the practical limit is the communication cost of averaging gradients, not the math."

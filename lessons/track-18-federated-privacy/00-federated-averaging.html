Federated averaging: training without pooling data

Your phone's keyboard learns from your typing, a hospital's model learns from its patients — but the raw data can't be collected in one place. Federated learning trains a shared model anyway: each device trains locally and only the weights are combined.

Track 17 · Lesson 0 Concept + code + interactive ~19 min Builds on: Track 6

Almost everything you've built assumed the data sits in one place where a model can see all of it. But some of the most valuable data can never be pooled: the messages on your phone, the patient records in a hospital, the transactions at a bank — privacy laws, trust, and sheer volume forbid shipping it all to one server. Federated learning is the breakthrough that trains a shared model without the data ever leaving its owner. The recipe, called Federated Averaging (FedAvg), is elegantly simple: the server sends the current model to each client (phone, hospital, bank); each client trains it a little on its own private data; each sends back only the updated weights (never the data); and the server averages those weights into a new global model. Repeat, and the shared model learns from everyone's data collectively while every raw example stays home. This flips the usual "bring the data to the model" into "bring the model to the data," and it's how Google trains your keyboard, how hospitals collaborate on medical AI without sharing records, and a foundation of privacy-preserving machine learning. This lesson builds FedAvg and shows it matching a model trained on all the pooled data.

💡 Intuition: study groups that never share notes

Imagine several study groups preparing for the same exam, but each is forbidden to share its private notes with the others. How can they collectively get smarter? Here's a way: everyone starts from the same summary sheet. Each group studies its own notes for an hour and updates the summary. Then they meet and average their updated summaries into a new shared one — no raw notes exchanged, just the distilled understanding. Repeat a few times, and the shared summary reflects what all the groups learned, even though no group ever saw another's notes. FedAvg is exactly this: the "summary sheet" is the model weights, "studying private notes" is local training, and "averaging summaries" is the server combining weights.

Formally, one round of FedAvg is: broadcast the global weights \(\theta\), each client \(k\) locally trains to get \(\theta_k\), and the server averages (weighted by each client's data amount \(n_k\)):

\[ \theta_k \leftarrow \text{LocalTrain}(\theta,\ \text{data}_k), \qquad \theta \leftarrow \sum_{k} \frac{n_k}{n}\,\theta_k \] (0.1)

Each client \(k\) starts from the shared \(\theta\) and runs a few steps of ordinary gradient descent on its own data to get \(\theta_k\). The server then forms the new global model as the average of the clients' weights, weighting each by its share of the data \(n_k/n\) (a client with more data counts more). Only the \(\theta_k\)'s travel — the data never does. That single averaging step is the whole trick.

✍️ Worked example: FedAvg matches centralized

1
Centralized baseline. Train one model on all the data at once — the best case, if pooling were allowed. Accuracy: 0.962.
2
Federated setup. Split the same data across 10 clients. Each round, every client trains locally for a few steps starting from the global weights.
3
Average and repeat. The server averages the 10 clients' weights into a new global model and broadcasts it. Do this for 30 rounds.
4
Result. Federated accuracy: 0.962 — identical to centralized, with no data ever pooled. When client data is similar (IID), averaging weights is almost as good as averaging data. (When it isn't, trouble starts — that's the next lesson.)

🛠️ From scratch: FedAvg

w, b = np.zeros(4), 0.0
for round in range(30):                         # communication rounds
    ws, bs = [], []
    for shard in client_shards:                 # each client = a private data shard
        lw, lb = train_local(X[shard], y[shard], w, b)   # local training, data stays put
        ws.append(lw); bs.append(lb)            # only weights are sent back
    w = np.mean(ws, 0); b = float(np.mean(bs))  # server AVERAGES the client models

# federated accuracy 0.962  ==  centralized accuracy 0.962   (no data pooled)

The only communication is ws.append(lw) (weights up) and the broadcast of the averaged w (down). The raw X[shard] never leaves the loop that represents a client. That's the entire privacy benefit of the basic scheme: data stays home, only models travel. (Basic FedAvg alone isn't a full privacy guarantee — the updates can still leak — which is why the later lessons add differential privacy and secure aggregation on top.)

Why averaging weights even works. It's not obvious that averaging two neural networks' weights gives a sensible network — in general it doesn't. FedAvg works because every client starts each round from the same global weights and takes only a few local steps, so the client models stay close to each other and close to the starting point. Averaging nearby models is like averaging small gradient steps — it approximates one big step on the combined data. Start clients from different places, or let them train too long locally, and the averaged model degrades (the "client drift" of the next lesson). Frequent syncing keeps them aligned.

⚠️ Mistakes everyone makes here

  • Thinking FedAvg alone is fully private. Data stays home, but the shared weight updates can still leak information about it (even reconstruct examples). Real privacy needs the DP and secure-aggregation tools in later lessons.
  • Letting clients train too long locally. Many local steps make client models drift apart, and averaging drifted models hurts. There's a sweet spot between communication cost and drift.
  • Forgetting to weight by data amount. A client with 10× the data should count 10× in the average (\(n_k/n\)); a plain unweighted mean over-weights small clients.
  • Assuming clients are always available and honest. Real deployments deal with phones dropping offline, slow stragglers, and even malicious clients — practical FL has to be robust to all three.

🔑 Key results to remember

  • Federated learning trains a shared model while data never leaves each client — "bring the model to the data."
  • FedAvg: broadcast global weights → clients train locally → server averages the weights (weighted by data amount, eq 0.1) → repeat.
  • Only weights travel, never raw data.
  • With similar (IID) client data, FedAvg matches centralized accuracy (0.962 = 0.962).
  • Averaging works because clients start from the same weights and take few local steps (stay aligned); it isn't full privacy by itself.

✍️ Practice

1. (warm-up) In the interactive, run several rounds and watch the three local boundaries versus the global one. What does the global boundary do relative to the three, and why does it improve over rounds?

Show solution

The global boundary sits roughly at the average of the three local boundaries, and over rounds all four converge toward the true split. Each round, the clients start from the shared global model and nudge it toward their own data; averaging those nudges is like taking one combined step informed by all three datasets, so the global model steadily improves — as if it had trained on the union, even though it never saw it. This is FedAvg working: the averaging aggregates everyone's learning signal without aggregating their data.

2. (transfer) Communication (sending weights back and forth) is often the bottleneck in federated learning, not computation. Given that, would you have clients do more local training steps per round or fewer? What's the tension?

Show solution

More local steps per round means fewer rounds (less communication) to reach a given accuracy — good when the network link is the bottleneck. But more local steps also let client models drift further apart before they're averaged, which hurts the averaged model, especially on non-IID data. So there's a direct tension: local computation is "cheap" and saves communication, but too much of it causes client drift and degrades the global model. The practical answer is to tune the number of local epochs to the sweet spot — enough to cut communication, not so much that drift dominates — and, on non-IID data, to use drift-correcting methods (next lesson). It's a communication-vs-accuracy trade-off unique to the federated setting.

3. (stretch) A "malicious" client could send poisoned weights to sabotage the global model. Why is this a real threat in FedAvg, and sketch one defense.

Show solution

It's a real threat because the server blindly averages whatever weights clients send, and it can't inspect their private data to check honesty — so a malicious client can submit a large, adversarial update that pulls the average toward a bad model (a "model poisoning" attack), potentially inserting a backdoor. Defenses replace the plain mean with a robust aggregation rule that resists outliers: use the coordinate-wise median or a trimmed mean instead of the mean, "Krum" (pick the update closest to its neighbours, discarding far-off ones), or norm-clipping (cap each update's size so no single client can dominate). More broadly, anomaly detection on updates and reputation systems help. The core lesson: any system that aggregates untrusted contributions needs robustness to adversarial ones, and secure aggregation (Lesson 4) — which hides individual updates — has to be balanced against the server's ability to detect bad ones.

🚀 In the real world & at the frontier

Federated learning is deployed at scale: Google trains the Gboard keyboard's next-word prediction across millions of phones without collecting your keystrokes; Apple uses it for on-device personalization; hospitals form federations to train diagnostic models on their combined patient data without sharing records; and banks collaborate on fraud detection across institutions. The frontier tackles the hard parts — non-IID data (next lesson), communication efficiency (compressing updates), robustness to dropped and malicious clients, and layering on formal privacy (differential privacy and secure aggregation, the rest of this track). Federated learning is a cornerstone of privacy-preserving AI: it shows that "learn from everyone's data" and "keep everyone's data private" need not be in conflict.
